# 率土之滨 每日任务自动化

在 MuMu 模拟器（MuMu 12 / Nx 内核，1920×1080 横屏）里自动完成每日领取。

技术路线：**ADB 截图 → Windows 原生 OCR 定位文字 → 按文字点击**，而不是死磕固定坐标。
每一处点击都有「多候选点 + 点击后校验 + 失败换下一个」的兜底链。

## 一、六个任务

| key | 任务 | 入口路径 | 干什么 |
|---|---|---|---|
| `gongpin` | 贡品礼包 / 月卡礼包 | 主城 → 活动 → 充值好礼 → 贡品礼包 | 领每日玉符 |
| `shuishou` | 内政税收 | 主城 → 内政 → 税收 | 领金币，每天最多 3 次 |
| `shijing` | 内政市井 | 主城 → 内政 → 市井 → 宝物商队 | 领免费物品；指定材料能用铜钱买就买 |
| `yanwu` | 内政演武 | 主城 → 内政 → 演武 → 右下角扫荡奖励 | 领每日「扫荡奖励」（纯领取，不花钱） |
| `texing` | 内政特性 | 主城 → 内政 → 特性 | 免费抽 1 张（**只在 12:00 档**） |
| `recruit` | 招募 | 主城 → 招募 → 卡包 | 先抽免费；半价按配置决定 |

档位：`00:00` 跑 5 个（除特性），`12:00` 跑全部 6 个。

### 什么时候跑：不再用 Windows 计划任务

2026-09-19 改的。原因：这台电脑不是全天开机，用户自己有「定时开机」的机制，
再在 Windows 里注册一套 00:00 / 12:00 的计划任务纯属重复，而且 WorkBuddy 不在时
也拿不到播报。所以：

- **删掉了** `install_schedule.py` / `setup_schedule.bat`，并注销了
  `STZB_Daily_0000` / `STZB_Daily_1200` 两个任务（已确认系统里搜不到任何 STZB 任务）
- 触发交给**用户自己的机制**调 `run_daily.bat`（静默启动器，输出进 `logs\console.log`）
- 磨合期由用户在对话里发出指令，我手动跑、看报告、修问题
- 结果不再靠定时播报，而是**推送到后端控制台**（见第十四节）

`run_daily.py` 里的「今天这一档跑过就不再跑」（`state\last_run.json`）保留 ——
无论谁触发，同一档一天只跑一次；要强制重跑加 `--force`。

### 两种运行模式：独立运行 / 后端托管

脚本既能被后端托管，也能**完全不绑后端独立运行**。**默认是独立运行。**

```python
# run_daily.py
MODE_STANDALONE = "standalone"   # 不连后端：报告只留本机
MODE_MANAGED    = "managed"      # 后端托管：拉配置 + 领任务 + 上传

def resolve_mode(cfg, offline, log):
    if offline:                                # 1. --offline 优先级最高
        return MODE_STANDALONE
    if not cloud.get("enabled"):               # 2. 出厂默认就是 False
        return MODE_STANDALONE
    if not base_url or not token:              # 3. 配不全就降级，并告警
        return MODE_STANDALONE
    return MODE_MANAGED
```

| | 独立运行 | 后端托管 |
|---|---|---|
| 开启方式 | 出厂默认；`--offline`；环境变量不设 | `cloud.enabled=true` + `base_url` + `token` |
| 远端配置 | ✗ | ✓ 只拉业务开关 |
| 待执行任务 | ✗ | ✓ |
| 上传 | ✗ | ✓ |
| 需要联网 | **完全不需要** | 需要（连不上也照跑，只是不上传） |

三条设计原则：

1. **独立运行是真的一个字节都不外发** —— 不是「连不上就算了」，而是那三条路
   （拉配置 / 领任务 / 上传）**根压根不会被走**。自检里有个
   「任何后端方法被调用就 raise」的假客户端守着这条。
2. **配不全自动降级**，不卡在重试里。比如只填了地址没填令牌 → 按独立运行处理并告警。
3. **托管模式下后端挂了也不影响跑任务** —— 任务照跑、报告照落本机，
   事后 `--upload-last` 补传。

所以把整个项目拷到另一台电脑、不配任何后端，装好 MuMu 和依赖就能直接跑。
`run_daily.py --status` 会明确告诉你当前是哪种模式、后端通不通。

### 本机配置工具（`tools/config.py` + `config_tool.bat`）

用户会想要「一个能配所有东西的工具」—— 不用去手改 config.json。
这是个**可选工具**：它只读写 `config.json`，删掉它、不用它，脚本照常跑。

设计要点（都是踩过坑才明白的）：

1. **一个 schema 驱动全部**：`Field` 表定义了每一项的类型 / 取值范围 / 中文说明 /
   服务端是否可覆盖。交互菜单、命令行 `set` 的校验、帮助文字全由它生成 ——
   加一个新配置项只需要加一行 `Field`，不用改三处。
2. **读原始 JSON、只改目标键、原子写回**：绝不重写整个文件。
   `config.json` 里有大量 `_说明` 注释键，重写就把文档弄没了；只改目标键则原样保留。
3. **写入前自动备份**（`state/config_backup/`，保留 10 份），提供 `restore`。
4. **绑定 = 当场验证**：填地址和令牌后先 `ping` + 拉一次配置，通过才写入；
   失败要把原因翻译成人话（401=令牌错 / 404=地址错 / 10061=没连上 / 证书=…），
   并明确「没有写入任何配置」。
5. **校验分 hard/soft 两类**：`abc` 填进整数项是**错误**，--force 也不能绕过；
   路径不存在是**可能有意为之**（比如准备之后再装 MuMu），交互模式追问一句、CLI 加 --force。
6. **中文对齐要按显示宽度**：`%-30s` 按字符数补空格，中文双宽字符会把表格撑乱。
   自己写 `disp_width` / `pad`，中文字符算 2 列。
7. **服务端接管提示**：读 `state/remote_config.json`，如果服务端下发过配置，
   工具会列出被接管的段并提示「改本地是没用的」—— 否则用户改了半天没反应，
   会以为脚本坏了。

命令行用法（给脚本 / 远程指导）：

```bat
python tools\config.py show
python tools\config.py show --section cloud
python tools\config.py set recruit.half_price false
python tools\config.py get shuishou.max_times
python tools\config.py reset recruit.half_price
python tools\config.py bind --url https://xx --token stzb_xx
python tools\config.py unbind
python tools\config.py verify

```

自检第 27 组专门守着它（schema 覆盖率、校验矩阵、_说明 不被破坏、
校验失败不写文件、交互菜单喂按键真能改到文件、备份轮换）。

> **00:00 那次是最重要的**：游戏的每日刷新点是 00:00，只有这一轮才能真的领到
> 「演武扫荡奖励」和当天的税收/招募次数。12:00 那轮多数会显示「已领过 / 冷却中」，
> 那是**正常结果**，不是故障。

## 六、安全铁律（写在代码里，不靠自觉）

1. **绝不花玉符/虎符**，唯一例外是 `recruit.half_price=true` 时的半价抽卡，
   而且必须同时满足「按钮左边缘有『打折』红丝带（或卡包列写『半价1次』）」
   **且**「价格读得出来、且 ≤ `half_price_max_hufu`」。
   价格读不出来一律不抽 —— 宁可漏抽一次，也不能按原价 200 买。
   虎符不够时会弹「虎符不足」，按 1 玉符=1 虎符 兑换，每次最多换 `hufu_buy_max` 个。
   这个弹窗也要先验明正身才点：(a) 必须读到「兑换比例 / 还需要…虎符」字样；
   (b) 弹窗里出现「充值 / 支付 / ¥ / 元宝」任一 → 一票否决直接关掉；
   (c) 兑换比例不划算（付 > 换到）→ 不点；(d) 「批量购买」永远跳过，只点带价格的
   「100 / 购买」，且价格 ≤ `hufu_buy_max`。
   读到原价 200 会直接放弃。
2. **绝不点真钱按钮**：`¥30/续期`、`支付`、`立即购买` 等都在 `never_tap` 黑名单里。
   注意别往黑名单加「充值」「购买」——会误伤「充值好礼」页签和市井购物这类正常操作
   （`selftest.py` 第 10 组就是专门守这条的）。
3. **税收只点免费的「征收」**。带数字的「20/征收」和「强征 / 20/强征」都是花虎符
   加速，永不点；格子标题行的「征收」也不是按钮（靠 y 坐标区分）。
   **状态不明的格子一律不点**（见第七节「盲点代价」）。
4. **特性只抽免费的那张**。按钮变成「立即获取 + 100」就放弃；
   倒计时文案「17:17:24后可免费获取1张」不会被当成按钮。
5. **出现「确定退出率土之滨」一律点「取消」**，绝不点「退出」。
6. 资源下载弹窗只点右上 ✕ 关掉，**绝不点「开始下载」**。
7. 关「居中的确定键」式信息弹窗（如「名望升级」）前，会先扫一遍屏幕上有没有
   「购买 / 充值 / 支付 / 虎符 / 玉符 / ¥ / 续期」等字样——**有就绝不动手**。
8. 每一步都截图存到 `logs\shots\`，事后可逐张倒查。

## 七、为什么这么写（踩过的坑）

### OCR 认不出游戏的美术字体

`stzb/core.py` 里有两张表：

- `_OCR_SWAP`：形近字替换。`犄/持 → 特`、`橈 → 税`、`巿 → 市`、`鼠 → 即`、
  `丬/氵/正 → 征`、`攵/収/攴 → 收`。
- `_OCR_DROP`：OCR 把字拆开时多出来的噪声字（`叫`、`鞋`），**只在待识别文本里删**。

> ⚠️ `_OCR_DROP` 绝不能作用于关键词。踩过一次：锚点「特鞋」被删成单字「特」，
> 成了「特性」的子串，于是内政主界面上的入口「犄性」被误判成
> 「已经在特性面板里了」，**导致那天的免费特性根本没抽**。
> 现在 `fix_ocr(text, drop=True)` / `fix_ocr(keyword)` 分开调用，
> `selftest.py` 第 8 组守着这条。

### 模糊匹配必须卡长度

`match_score()` 里，长度差超过 30% 就一律不算模糊匹配。
否则主城右下角的「招募」会被算成「招募1次」（相似度 0.667），
把主城误判成招募卡包详情页，`to_home()` 就永远退不回去。

### 「已征收」红章 OCR 读不出来

税收面板的「已征收」是斜着盖的红章（约 -15°），4 帧 OCR 合并也读不到。
所以改用颜色兜底 —— 实测数据：

| 目标 | 面积 | 外接框 |
|---|---|---|
| 斜盖章 | 1036 | 141×78 |
| 付费按钮上的「征收」小红字 | 264 | 22×30 |

判据是「面积 ≥ 600 **且** 宽 ≥ 100」，两者干净分开。
**不要加形态学膨胀**：9×9 的 CLOSE 会把付费按钮那几个小红字连成 713px 的大块，
直接造成误判。

### 盲点固定坐标的代价（2026-09-18 踩到）

税收的老写法对「状态不明」的格子回退到固定坐标 `(427, 880)` 盲点一次。
那天那一格正好是「20/强征」，点下去直接弹「虎符不足」——**虎符够的话就白花 20 虎符**。
现在**彻底取消盲点**：三条路都不确定就什么都不做，只打一行日志。
宁可漏领一次，也不能乱花钱。

配套加的第三重手段是 `ocr_image_scaled()`：把截图放大 2 倍再 OCR。
游戏里按钮文字高度常只有 20px 上下，原生分辨率会整条漏读，放大后能读出来。

### 「强征」按钮的第二重判据（纯颜色）

「20/强征」的 OCR 结果极不稳定（原生读不出，放大 2 倍读成「0/弓征」），
所以再给它一条颜色判据。实测指纹（1920×1080）：

| 槽位状态 | 亮红连通块 | 按钮行白色占比 |
|---|---|---|
| 「已征收」斜盖章 | 面积 1036、宽 141 | — |
| 「20/强征」付费键 | 两段各 265、宽 22 | **0.655** |
| 「等待中···」 | 没有红块 | 0.02 |

判据「有小红字（100 ≤ 面积 ≤ 600 且宽 ≤ 60）**且** 白色占比 ≥ 0.30」= 付费键。
和红章（面积 ≥ 600 且宽 ≥ 100）互斥，不会撞车。
`selftest.py` 里可以喂空 OCR 结果、只给图片，验证纯颜色也能判对。

### OCR 会把相邻标签连读成一个框

主城顶栏被读成「活动36小时」，框 `(273,164)-(441,187)`，
框中心 `(368,175)` 落在**隔壁那个 36 小时 buff 图标**上 —— 点下去开的是
「初出茅庐」buff 详情页，面板一盖，后面 4 次重试全打在遮罩上，
整个贡品礼包任务就废了。

修法是 `Ui._kw_point()`：如果命中的关键词只是框内的**前缀**，
就按字符长度占比取它自己那一段的中点（`活动36小时` → 取左侧 1/3 → x≈304）。

`click()` 还加了一条自愈：**上一次还看得见目标、这次却看不见了**，
且**不在主城**、**不在内政主界面**、**能明确认出当前停在别的面板上**
→ 判定为「误开了别的面板」，先按右上 ✕ 退出来再继续重试。

> ⚠️ 三个附加条件一个都不能少：
> - 「上一次看得见」——否则 OCR 单纯读不出来时会误触发；
> - 「不在内政主界面」——内政那个 ✕ 位是**返回键**，点它等于把刚打开的内政关掉，
>   后面所有候选坐标就全打在主城上、必然全失败（踩过，整轮税收/市井/特性报废）；
> - 「认得出当前在别的面板上」——否则在内政里也会误判。

### 不带「取消/跳过/关闭」的信息弹窗

「名望升级 / 解锁新功能」弹窗只有一个居中的「确定」，没有右上 ✕。
老 `boot()` 会一直「等待中…」直到 300 秒超时 —— 就是那种「突然卡壳」。
现在 `guard()` 里专门认它，`boot()` / `to_home()` 里还各挂了一层
`close_info_popup()` 兜底（任何居中确定键都能关，但带消费字样就绝不动手）。

### 内政面板会「呼吸式」漂移

固定坐标会偏 ±20px，所以每次点击前**当场 OCR**、用同一份结果的坐标去点。

> 内政里的入口真正可点的是**名字标签（斜六边形）本身**，不是旁边的菱形图标。
> 曾经把点击点整体上移 65px 去点菱形图标（`NZ_ENTRY_ICON_OFFSET`），
> 结果 6 个候选坐标全失败；点标签中心 `(1770,600)` 一次就进。
> 现在这个偏移表是空的，`NZ_ENTRY_FALLBACK` 按「标签中心优先」排列。

### 特性/税收面板文字盖在动态插画上

单帧 OCR 会整行糊掉，用 `ocr_multi()` 多截几帧取并集。

## 八、图形判据：OCR 读不出来的按钮怎么认（2026-09-19 新增）

### ⚠️ 先记住这条：Windows 原生 OCR 有「最小尺寸门槛」

**小于约 480×270 的图，OCR 直接返回 0 行，而且不报错。**

| 喂进去的尺寸 | 读出的行数 |
|---|---|
| 320×180 | **0** |
| 480×270 | 9 |
| 640×360 | 14 |
| 960×540 | 25 |
| 1280×720 | 33 |
| 1920×1080 | 33 |

后果很坑：诊断时裁一个 190×75 的按钮区域去 OCR，得到 0 行，
会得出「OCR 读不出这个词」的**错误结论**（其实是图太小）。

- 要放大就放大**整张图**（`ocr_image_scaled(factor=n)`），**别先裁再放**；
- 确实只想要某一块，就先把那一块 resize 到 ≥480×270 再存盘再识别。

### ⚠️ 第二条同样重要：OCR 的框会「飘」，飘的时候按颜色点

演武右下角那行「扫荡奖励」，**同一块静止面板连拍 5 帧**，OCR 框中心是这样的：

| 帧 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|
| 框中心 y | 981 | 1005 | 1012 | 1036 | 1041 |

60px 的漂移。原因不是面板在动 —— **是 OCR 经常把下面那行倒计时并进同一个框里**，
框变大了，中心就往下跑。拿这个中心去点，正好落在「宝箱图标」和「文字」**之间的空隙**上：
真机连着三次全打偏（`(1749,999)`、`(1713,1056)`、`(1746,1005)`），一次都没弹出奖励框。

同一块面板上，宝箱的金色块却**一动不动**：连拍 5 帧都是 `(1718,874)-(1799,938)`，
81×64、面积 2917。点它中心 `(1758,906)`，一次命中。

所以结论是：

> **OCR 给的是「文字在哪」，不是「按钮在哪」。**
> 一个元素的 OCR 框如果会飘（位置变、被并框、漏读），就别拿它的中心当点击点 ——
> 找一个**几何上稳定的**代理特征（颜色块、图标形状、进度环）来定位。

定位宝箱的代码在 `stzb/tasks.py` 的 `_find_sweep_icon()`，几个必须卡住的点：

```python
YW_ICON_BOX = (1660, 1860, 840, 980)   # 窗口贴紧宝箱，别放宽
YW_ICON_MIN_AREA = 1200                # 面积下限（宝箱 2917）
YW_ICON_W = (50, 130)                  # 宽
YW_ICON_H = (40, 100)                  # 高
# 金色区间 HSV [15,70,130]~[40,255,255]
```

窗口和长宽比都得卡死 —— 面板背景里有**一块又宽又扁的金色山岩**（实测 195×41），
HSV 阈值一放松它就会冒出来抢第一名。`selftest.py` 第 19 组专门放了这块干扰做回归。

### 市井「免费」按钮：白块里没字、但有墨

OCR 就是读不出「免费」两个字（1×/1.5×/2×/3× 全试过）。
改成按形状认：「**一个白底按钮块里没有任何 OCR 文本、但里面确实有墨**」→ 就是免费键。

- 抠块：HSV `inRange([0,0,215],[180,45,255])` → `connectedComponents`，
  卡 `140 ≤ 宽 ≤ 212`、`36 ≤ 高 ≤ 62`、y 落在栅格 `(250,660)`；
- 「有墨」= 块内暗像素占比 > 0.03；
- **同一页找出 ≥2 个「无字白块」就什么都不点**（说明判据不可靠）。

### 市井价格：图标在按钮**正上方**，不在左右

「赤珠山铁」是**玉符 700**，老逻辑只看同行水平间隙 → 那里根本没有图标
→ 判成铜钱价 → 点下去弹「虎符不足」（虎符够就真花了 700 玉符）。

现在按按钮**上方**的横条 `x1-20, y1-85, x2+20, y1-3` 取价格带：

| 价格类型 | 价格带绿色占比 |
|---|---|
| 玉符（绿） | **0.053** |
| 铜钱（黄） | 0.000 |

- 绿色占比 ≥ `SJ_JADE_MIN`（0.02）→ 玉符价，**绝不买**；
- 价格带里读不出 ≥3 位数字 → **绝不买**。

### 招募「免费」徽标：按钮左侧的绿色小圆角块

同样读不出字。改成在「招募1次」按钮**左侧**找饱和绿小圆角标签：

- 搜索区域：`dx ∈ (-150,-50)`、`dy = 55`（相对按钮）；
- HSV `inRange([35,120,120],[90,255,255])`；
- 面积 ≥ 250、`22 ≤ 宽 ≤ 80`、`18 ≤ 高 ≤ 55`；
- 实测真徽标 40×32、面积 639，约在按钮左侧 106px、下方 23px。

顺序是：先读字 `near(items,"免费",btn,…)` → 读不出再找绿徽标。
`selftest.py` 第 15 组守着「远处绿块不算」「拿『招募5次』当参照必须为 False」。

### 招募「打折」红丝带 + 价格在按钮的**第二行**（2026-09-19 新增）

这是「半价没抽」这个 bug 的两个根因：

1. **竖排的「打折」二字 OCR 完全读不出来。** 那是一条白色竖排字压红底的丝带，
   长在「招募1次」按钮的左边缘；整帧 OCR 里根本没有「打折」这两个字
   （实测 `rc_free_panel_*.png` 十几次截图一次都没读到）。
   → 改用颜色+形状认，实测指纹：

   | 目标 | 外接框 | 面积 | 高/宽 |
   |---|---|---|---|
   | 红色「打折」丝带 | 40×85 | 2491 | 2.12 |
   | 按钮里的价格红字「100」 | 16×22 | 133 | 1.38 |

   判据：`面积 ≥ 600` **且** `25 ≤ 宽 ≤ 70` **且** `55 ≤ 高 ≤ 130` **且** `高 ≥ 1.5×宽`
   （红 hsv 0–10 / 170–180，s≥120，v≥120）。面积差 18 倍，不会撞车。

2. **价格在按钮白块的第二行，不在左右。** 「招募1次」按钮是两行结构：
   第一行是文字，第二行是「币种图标 + 价格」。老代码 `_price_left_of` 只往左侧找，
   永远读不到 → 价格检查形同虚设（读不到还会放行，更危险）。
   → 换成 `_price_under_btn`：按按钮框下沿往下 85px 内找数字。

**实测对照（同一批真机截图，判据 100% 一致）：**

| 状态 | 红丝带 | 读到价格 | 卡包列字样 |
|---|---|---|---|
| 半价可用 | **True** | **100** | `00（半价1次）` |
| 半价已用完 | False | **200** | 无 |

另外注意：**免费状态下的丝带是同一形状但是绿色的**（所以「免费」也用同一套形状判据，
只是换成绿色掩码），而且免费状态下按钮只有一行、**没有价格行**。
所以免费态天然读不到价格 —— 这也正是「读不到价格就不抽」这条安全阀不会误伤免费抽的原因
（免费走的是 `is_free` 分支，压根不做价格检查）。

`tools/probe_recruit.py` 可以只「看」不抽地验证这套判据：
它会打开招募面板、把三个信号打印出来、然后退回主城，**绝不点任何抽卡按钮**。

### 关面板的锚点词必须是这个面板独有的

市井的锚点原来写成 `("宝物商队","贡献","名师","荣誉")`，
可**主城顶栏永远挂着「荣誉 30/30」** → 关面板循环永远等不到锚点消失，
只能把 5 个候选坐标全点一遍（**每个面板白花 30 秒**），还会误点开别的面板。
现在锚点只用面板专有词，`_try_closes()` 开头还加了「已经在主城就直接返回」。
实测耗时：贡品 35→17s、市井 33→12s、招募 12→6s。

### 判断「我在哪个界面」必须和主城特征互斥

主城上点一下资源数字会弹「铜钱」说明浮层，里面有「**内政税收 · 免费征收**」
「前往市井」——凑够两个锚点就能把 `is_neizheng` 骗成 True，
于是「进入内政」一个点击都没发就返回成功，后面全错位。

同理内政主界面上挂着状态标签「**立即征收N/3**」含「征收」二字，
会被 `_in_panel("税收")` 当成「已经在税收页里了」→ **税收任务静默跳过、0 次征收，还报成功**。

两个修法合起来：
- `is_neizheng()` / `_in_panel()` 第一句都先 `if self.is_home(items): return False`；
- 加 `_is_neizheng_screen()`（认「立即征收」+ 锚点计数），`_in_panel` 先过它；
- 税收面板的正判据改成 `_count(items,"征收") >= 2`（面板有 3 个格子标题，主界面只有 1 处）；
- 内政入口的点击校验一律用 `verify_fn=lambda its: self._in_panel(name, its)`
  判「是否**真的进了面板**」，而不是「有没有出现某个词」——
  用词校验踩过：verify 列表里的「征收」在内政主界面就有，
  第一个候选点刚点完就立刻判定「生效」，剩下 4 个候选点根本没机会试。

**反过来也一样：`is_home()` 得排除子面板。** 演武面板上写着「Lv.4土地」，
而主城顶部的滚动公告栏会冒出「恭喜 xx **招募**到5星武将」——「土地 + 招募」
正好凑齐 `is_home` 的两个条件，**整块演武面板被判成主城**。

后果：`open_sub("演武")` 认为没进去 → `to_home()` 重来 → 白花 35 秒，
而且 `to_home()` 还会把演武上的复选框「**跳过**战斗动画」当成关面板键连点 5 次
（`("取消","跳过","关闭")` 三个关键词里「跳过」命中了它）。

修法：
```python
# is_home 里，子面板特征词一律先排除
if self.has(items, "同步主城队伍", "守军难度", "跳过战斗动画",   # 演武
            "宝物商队", "剩余特性", "获取1张",                  # 市井 / 特性
            "已征收", "征收中", "加速获取"):                    # 税收
    return False
# 关面板的关键词命中时，再排掉「跳过战斗动画」这个复选框
if "动画" in hit.text:
    continue
```

> 教训：`is_home`（我在主城）和「我在某个面板里」**必须严格互斥**，
> 而且这个互斥要在**两边**都写。只在一处防，另一边迟早会漏。
> `selftest.py` 第 20 组守着这两条。

**还有一条：认不出的面板不能干等。** 实测被「政务」面板卡死过一整轮 ——
它没有写锚点，`_screen_anchors()` 返回空，老代码就只点 `cands[0]=(1832,53)` 一下，
而政务面板的 ✕ 在 `(1778,155)` 附近，于是**干等到 300 秒启动超时**。
更坑的是它上面还压着一条「顶部选中条」（`将【魏·郝昭·步】`）会**吞掉面板 ✕ 的点击**，
得先点它自己的 ✕ `(1325,76)`。

修法两条一起上：

```python
# ① 锚点为空 = 认不出的界面 → 把右上角那串 ✕ 候选全试一遍，每点一次回头确认
else:
    self.log("    · 认不出的界面 → 依次试右上角 ✕")
    for c in cands:
        self.tap(*c, delay=0.0)
        time.sleep(1.5)
        items2, _ = self.ocr("closeunk")
        if self.is_home(items2):
            return True
        if self._screen_anchors(items2):
            break                  # 已经切到认得出的面板，交给外层循环

# ② boot() 里加一条兜底：等 8 轮还认不出界面就强制清屏，别干等到超时
elif rounds >= 8:
    self.log("    · 等了 %d 轮仍认不出界面 → 强制清屏退回主城" % rounds)
    self.to_home(max_rounds=5)
```

全量跑的时候这条还真的救了场：特性任务退面板时日志出现「认不出的界面 → 依次试右上角 ✕」，
然后就回主城了。

## 九、单实例锁（2026-09-19 新增）

`run_daily.py` 启动时会抢 `state/run.lock`，抢不到就直接退出（退出码 2）。

为什么必须有：00:00 那轮定时跑到 00:03:05 才结束，而手动那轮 00:02:04 就起了，
**重叠 61 秒** —— 两个进程同时 ADB 点击、日志交错、步调互踩，**所有点击全部打偏**。
这不是「偶尔不准」，是必崩。

- 锁文件内容：pid + 启动时间戳；
- 判活：`kernel32.OpenProcess(0x1000, …)` + `GetExitCodeProcess == 259`（STILL_ACTIVE）；
- `atexit` 时自动删除锁文件；
- pid 已死、或锁超过 `LOCK_STALE_SECONDS`（1800s）→ 自动接管，不会永久卡死；
- 日志里会写「已有一个实例在运行（pid=…）」。

`selftest.py` 第 16 组守着这条：抢锁、挡重复、释放删文件、接管死 pid、接管过期锁。

## 十二、冷启动与执行报告（2026-09-19 新增）

### 为什么用 MuMuManager 而不是双击 MuMuPlayer.exe

双击只能「把模拟器打开」，脚本没法知道它什么时候真的起来，也没法知道该不该开。
MuMu 自带的命令行长这样：

```bat
MuMuManager.exe info    -v 0                              rem 返回 JSON 状态
MuMuManager.exe control -v 0 launch --package <包名>       rem 起模拟器 + 顺带起游戏
MuMuManager.exe control -v 0 shutdown                     rem 关掉这台虚拟机
MuMuManager.exe main    kill                              rem 收掉主程序窗口
```

`info` 返回的 JSON 里有三个关键字段，**必须都看**：

| 字段 | 含义 | 为什么要看 |
|---|---|---|
| `is_process_started` | 虚拟机进程在 | 判断「要不要启动」 |
| `is_android_started` | Android 起来了 | 只看这个还不够 |
| `player_state` | 到达 `start_finished` 才是真的开机完成 | **只有到这一步 adb 才连得上** |

#### 踩到的坑：`main kill` 会「成功地什么都没做」

主程序（GUI 窗口）没在跑、只有虚拟机进程时，`main kill` 返回成功但**虚拟机纹丝不动**。
第一次实测就是这样：以为关干净了，`status` 一看 `adb=127.0.0.1:7555` 还连着。
修法：`kill_all()` 里补一刀 `control shutdown`，再轮询 `is_running()` 确认。

#### 踩到的坑：`info` 里的 `adb_port` 不能用来拼 serial

`info` 报 `adb_port: 16384`，但实际游戏在跑的那台是 `127.0.0.1:7555`。
而且同一台 Android 会同时以 **两个 adb 传输通道**出现：

```
127.0.0.1:7555    device
emulator-5554     device     ← 和上面是同一台（实测 model / sdk 完全一致）
```

所以一律用 `config.json` 里的 `serial_candidates` 逐个探测，**永远不要拿 `adb_port` 去拼**。

#### 踩到的坑：MuMuManager 的输出是 GBK

按 UTF-8 解会全是乱码（虚拟机名会变成 `MuMu瀹夊崜璁惧��`）。
`emulator.py` 里统一 `decode("gbk", "replace")`。

### 启动游戏：先解析 Activity，再退回 monkey

```python
adb shell cmd package resolve-activity --brief com.netease.stzb.netease
# → com.netease.stzb.netease/.SomeActivity
adb shell am start -n <上面那串>
```

用 `am start -n` 而不是 `monkey`：能明确指定 Activity，而且游戏已经在后台时是
「拉到前台」而不是重走一遍开屏。`monkey` 只作兜底。

另外「游戏起来了没」不能靠点击成功判断，要轮询 `pidof <包名>`。

### 报告为什么要把截图转成 base64

| 方案 | 问题 |
|---|---|
| HTML 里引用相对路径 `shots/xxx.png` | html 单独拷走 / 发给别人就全裂 |
| 原图 base64 内嵌 | 单张 3MB、一轮上百张 → html 几百 MB，浏览器打不开 |
| **缩到宽 900px + JPEG q72 再内嵌** | 单张 60~120KB，整份 1~3MB —— 采纳 |

每个任务最多内嵌 5 张，挑法是 `_pick_shots`：**优先 tag 里带 `panel` 的（面板全貌）、
必含最后一张（最终状态）**，不够再按等间隔补，最后按拍摄时间还原顺序。

顺手踩的一个坑：一开始按**文件名**排序，结果 `sj_ok_02.png` 排到了
`sj_panel_01.png` 前面 —— 不同 tag 的前缀不一样，字母序和时间序根本没关系；
序号到 100 以后 `_100` 的字母序还小于 `_099`。改成按 `mtime` 排。

### 截图是按「文件差集」归到每个任务头上的

不改任务代码、不加埋点：任务开始前记一次 `logs\shots\` 的文件名集合，
结束后再记一次，**差集就是这个任务产生的截图**。副作用是 OCR 放大重试的中间产物
（`xxx.png.x2.png`）也会被算进来，所以过滤掉带 `.x2.` 的。

### 顺带修的一个清理逻辑

报告目录里有 `latest.json` / `latest.html` 和用户可能自己放的文件，
自动清理**只删 `run_` 前缀**的过期文件，别人放的东西一律不动（自检里有断言守着）。

## 十三、后端控制台（2026-09-19 新增）

跑完把结果、报告、截图推到一台公网服务器；在外面也能看结果、改任务、排下一次跑什么。

**技术栈**：Python 3.13 + FastAPI + SQLite + Jinja2（服务端渲染，无前端构建）。
**部署**：Docker Compose（应用 + Caddy 自动 HTTPS）。完整步骤见 `server/README.md`。

### 13.1 数据流

```
Windows 本机                                   公网服务器
────────────                                   ──────────
run_daily.py
  ├─ 1. GET  /api/agent/config   ← 拉业务配置（v 变了才应用）
  ├─ 2. GET  /api/agent/jobs     ← 看有没有排的待执行任务
  │     POST /api/agent/jobs/{id}/take   ← 领走（原子，重复领 409）
  ├─ 3. 冷启动模拟器 → 开游戏 → 进主城 → 跑任务 → 出报告
  └─ 4. POST /api/agent/run                    ← 上传结果，拿 run_id
        POST /api/agent/run/{id}/report        ← 上传报告 HTML
        POST /api/agent/run/{id}/shot  ×N      ← 上传精选截图（缩过的）
        POST /api/agent/run/{id}/done          ← 收尾，顺带清理旧记录
        POST /api/agent/jobs/{id}/ack          ← 给待执行任务回执
```

**上传是「尽力而为」**：网络断了、服务器挂了，只记一条日志，**绝不影响本机跑任务
和落盘报告**。恢复后用 `--upload-last` 从 `logs\reports\latest.json` 补传，
不用重跑一遍游戏。

### 13.2 ★ 安全边界：远端只能改「业务开关」

这是整套设计里最重要的一条。`config.json` 分成两类：

| 类别 | 段 | 谁能改 |
|---|---|---|
| **业务开关** | `tasks` / `recruit` / `shijing` / `shuishou` / `texing` / `yanwu` / `gongpin` / `safety` | 后端控制台**或**本机 |
| **本机设置** | `device`（adb 路径与端口）/ `emulator`（MuMuManager 路径、虚拟机索引）/ `cloud`（后端地址与令牌）/ `logging` | **只有本机** |

理由很直接：万一你在外面把配置改错了，**至少脚本还能连上模拟器、还能上报**，
你还有机会改回来。要是连 adb 路径都能被远端改，改错一次你就得跑回机房。

实现上是**两边各拦一遍**：`server/app/managed.py` 的 `filter_payload()` 先在服务端过滤，
`stzb/remote_config.py` 的 `filter_payload()` 再过滤一次。任何一边写错都不会把本机配置搞坏。
自检第 23 组专门守这条（含「服务端试图下发 `cloud.token`」这种攻击性用例）。

合并用**深合并**：只覆盖远端确实带了的键，本机多出来的 `_说明` 注释、同段其它键原样保留。
拉不到就**一行都不动**，只用本地配置（自检里有断言）。

### 13.3 上传为什么零第三方依赖

`stzb/cloud.py` 只用标准库（`urllib` + `ssl` + 手搓 multipart）。理由：
脚本要能在任何 Python 环境跑，不能因为少个 `requests` 就当场挂掉。

TLS 有个坑要专门绕：Windows 上 `ssl.create_default_context()` 可能只加载到很少的根证书。
所以优先用 `certifi` 的证书包（实测 121 个 CA，含 Let's Encrypt 的 ISRG Root X1/X2），
拿不到才退回系统默认。**两种都失败时直接报错**，绝不静默降级成不校验 ——
往公网传的是你游戏账号的自动化凭据，这事儿不能图省事。

### 13.4 报告 HTML 是「上传来的文件」，必须沙箱化

报告确实是我们自己生成的（内联 `<style>` + base64 图片，没有脚本），但它毕竟是
**从外部传进来的**。所以服务端提供它时：

```
Content-Security-Policy: default-src 'none'; img-src data:; style-src 'unsafe-inline';
                         font-src data:; form-action 'none'; base-uri 'none';
                         frame-ancestors 'self'
```

`default-src 'none'` 直接把脚本、外链、表单全掐掉，再放进 `<iframe sandbox>` 里渲染。
就算有人往报告里塞 `<script>`，也执行不了，更碰不到控制台的会话 Cookie。

### 13.5 踩到的三个坑

| 坑 | 现象 | 修法 |
|---|---|---|
| **scrypt 撞 OpenSSL 内存上限** | 首次启动直接起不来：`ValueError: memory limit exceeded` | `hashlib.scrypt` 要显式传 `maxmem`。默认只有 32MB，而 n=2^15,r=8 需要 128·n·r ≈ 33.5MB，差一点点就超 |
| **`TemplateResponse` 参数顺序变了** | 所有页面 500，`TypeError: unhashable type: 'dict'` | Starlette 1.x 的签名是 `(request, name, context)`，旧写法 `(name, context)` 会把 context 当成模板名 |
| **Jinja 里 `g.items` 不是键** | 配置页 500 | 字典的 `items` 属性会先于键被解析，拿到的是绑定方法。改名叫 `g.rows` |

前两个只有真机会暴露（自检跑不到），第三个是纯代码问题。都写进自检或文档了。

### 13.6 验证到什么程度

本机起服务（`127.0.0.1:8099`）跑通的：

- 上传真实那轮 6/6 OK 的结果：**运行 #1、报告 3.1MB、24 张截图**，全部落库
- 数据库核对：`runs` 1 行 / `task_results` 6 行 / `artifacts` 25 行（1 报告 + 24 截图）/
  `configs` 2 版本 / `run_requests` 1 行
- 配置读写：表单保存 → v1，`tasks.texing` 不勾选变成 `false`、材料清单从多行文本正确解析、
  `device`/`emulator`/`cloud`/`logging` **一个都没泄漏进下发 payload**
- 版本回滚：`/config/restore/1` → 生成 v2 并标注「回滚自 v1」
- 待执行队列：控制台新建 → 脚本侧 `GET /jobs` 看得到 → `take` 200 →
  **重复 take 返回 409** → `ack` 200 → 页面显示「已完成」并链到运行 #1
- 报告沙箱：`/runs/1/report` 返回 200 + 完整 CSP 头，`default-src 'none'` 生效
- 认证：无 token / 错 token 均 401；错口令 401 且不提示哪个字段错；未登录访问 `/` → 303 到登录页
- 截图代理：`/artifacts/N` 返回 `image/jpeg`，135KB

**没验证的**：Docker 镜像构建与 Caddy 签证书（本机没装 Docker，也没域名）。
这两个只能在你的服务器上验，`server/README.md` 里写了逐步自检方法。

## 十四、多客户端 / 多账号：探活、指派、切换（2026-09-19 新增）

### 14.1 核心矛盾：后端在公网，客户端在内网

这是整套设计的前提，所有「反直觉」的写法都来自它：

**服务端没法主动连客户端。** 家里的机器在内网、没有公网 IP，
服务端想「看它在不在线」「让它切个账号」——都做不到。

所以全部改成**客户端主动上报**：

```text
客户端                                    服务端
  │ POST /api/agent/heartbeat ──────────► 记 last_seen / IP / 版本 / 设备
  │ （每 30 秒）                            │
  │                                         │ 距今 > 90 秒 → 判掉线
  │ ◄──── assignment（该用哪个账号/角色）
  │       switch_needed（要不要切）
  │       command（有没有要执行的探测指令）
  │
  │ 按指派切换 → 跑任务 → 上传
```

两个直接推论：

1. **「在线」不是存出来的，是算出来的。** 库里没有 `online` 字段，
   `/clients` 页每次渲染时用 `now - last_seen` 现算。存字段会有一堆过期问题
   （进程重启、心跳停了、时钟漂移），算出来的永远自洽。
2. **「探测」= 服务端挂指令，客户端下次心跳取走执行。**
   实体上是 `clients.probe_json` 里塞一条一次性指令，语义上是「远程让它看一眼屏幕」。
   这比 RPC 麻烦，但它是唯一在 NAT 后面可行的做法。

### 14.2 ★ 账号切换的能力边界（实测，不是猜的）

摸界面时（`tools/probe_switch*.py`，产出在 `recon/switch4.json`）确认的事实：

| 动作 | 要密码吗 | 路径 |
|---|---|---|
| **换角色 / 换区服** | **不要** | 登录页「点击换区」→「选择服务器」→ 点角色 →「确定」 |
| **换账号** | **不要，但有限制** | 左上角图标 →「用户中心」→「切换账号」→ 落到**网易统一登录页** |

换账号这一步的细节是关键：

- 网易登录页上只有**「常用」列表**，里面是**这台机器登录过的账号**（脱敏显示，
  如 `159****4508`）。点一下账号、再点「登录」，就切过去了。
- **要切一个从没在这台机器登过的账号 → 必须人工输密码。本模块不做这件事，
  也绝不保存任何密码。**
- 所以约定写进了 README 和界面文案：**每个要自动切换的账号，至少先手动登录过一次。**

这个边界是**故意暴露给用户**的，不是绕过去：
切换不到时 `switch_account()` 返回的 reason 直接写「这个账号需要先在这台机器的
模拟器里手动登录一次」，而不是含糊地说「失败」。

### 14.3 两个危险按钮（踩过一次，差点中招）

登录页/游戏内按 **Android 返回键**会弹出问卷「请问，导致中途退出的原因是？」，
下面就是**「提交并退出」**。网易登录页上还有一个**「其他账号登录」**。

处理原则：

- 本模块**全程不按返回键**。一律用界面上的按钮 / 「继续游戏」。
- `NEVER_TAP` 黑名单 + `guard_survey()` 兜底：只要屏幕上出现「中途退出」，
  唯一的动作是点**「继续游戏」**（(427,837)）。
- `stzb/ui.py` 的 `guard()` 里还有第二道同样的防线 —— 两道都拦。

测试里专门有一条 `test_never_taps_dangerous`：按剧本先喂一个问卷屏，
断言**没有任何点击落在 (1350,837)「提交并退出」或 (960,813)「其他账号登录」附近**。

### 14.4 「未选择服务器」差点骗过面板判定（真实 bug）

拿真实 recon 数据核对时发现的：

登录页上有一行 `未选择服务器`，而它**包含**「选择服务器」这个子串。
原来的 `_open_server_panel()` 用子串匹配（`match_score` 里 `k in t` → 0.90+），
于是**登录页会被误判成「选择服务器面板已经打开」**，
接下来就在登录页上瞎找角色，自然找不到，报「找不到角色」——排查起来极其费解。

同类问题还有：`自动登录` / `上次登录刚刚` 都含「登录」，会让「是否在网易登录页」
的判断假阳性。

修法：

- 面板**标题**这类必须精确的判断，改用 `_exact()`（归一化后完全相等），
  不再用子串匹配；
- 「登录」按钮改用 `_find_login_button()` 精确找：先找整串等于「登录」的，
  再退回相似度 ≥0.8 且排除「自动登录 / 上次登录 / 其他账号登录」的。

回归测试：`test_login_page_no_longer_mistaken_for_panel` 直接断言
`_has(LOGIN, *KW_SELECT_SERVER)` 为 True（说明子串匹配确实危险）
而 `_exact(...)` 为 False（说明现在的判断是对的）。

> **教训**：`k in t` 这种子串匹配在中文界面上很危险 ——
> 中文没有词边界，任何短词都可能是长词的一部分。**判断「面板开没开」必须精确匹配。**

### 14.5 为什么把重依赖做成容错导入

`stzb/core.py` 原先在模块顶层 `import cv2` / `import numpy` / `from winrt...`。
后果是：**只想用里面的纯文本逻辑（`norm` / `match_score` / `TextItem`），
也得先装 OpenCV + WinRT**。写账号切换的单元测试时就被这个卡住了 ——
测试机上没 cv2，连 `from stzb import account` 都 import 不进去。

改成 try/except 容错导入 + `_need_vision()` 运行时守卫：

- 纯逻辑（归一化、模糊匹配、`TextItem`）：任何 Python 都能 import；
- 真要用图像/OCR：缺依赖时给出**可操作的报错**（写清装什么），
  而不是莫名的 `AttributeError: 'NoneType' has no attribute 'imdecode'`。

`stzb/report.py` 同理（只有「嵌缩略图」需要 OpenCV，拼 HTML 是纯字符串活）。

这不只是为了测试 —— 它让「渲染报告的机器」和「跑 OCR 的机器」可以不是同一套环境。

### 14.6 联调测出来的真实漏洞：定向任务越权

`tests/e2e_client_server.py` 跑出来的：一个**没带 uid 的客户端**（未注册）
请求 `GET /api/agent/jobs`，服务端把 `client_id` 当成 `None` 传下去，
而 `request_pending(limit)` 的老实现**无视 client_id、返回全部待执行任务** ——
于是未注册的调用者能看到、还能**领走别人定向的任务**。

修法：新增 `request_pending_for(limit, client_id)`，
`client_id is None` 时**只返回公共任务**（`WHERE client_id IS NULL`），
并且在 `job_take` 时**再查一次归属**（A 不能领 B 的定向任务，返回 403）。

修完的断言写进了 e2e 测试：

```text
另一台看到: {"jobs": [], "client_id": null, "registered": false}
B 抢 A 的定向任务: 403 (应 403)
```

`tests/test_guardrails.py` 里还有一条**源码级回归**：断言
`db.request_pending_for` 的实现里存在 `client_id IS NULL` 过滤 ——
防止以后有人「优化」掉它。

> **教训**：关于「谁能看到什么」的逻辑，必须用**两条不同的身份**去测。
> 单客户端测试永远是绿的，因为越权只在多客户端时才表现出来。

### 14.7 稳定客户端标识：为什么不能拿 hostname 当 ID

第一版想用 `socket.gethostname()` 当客户端 id，问题：

- 两台机器可能同名（默认 `DESKTOP-XXXX` 撞名率不低）；
- 用户改个机器名，后台就多出一条「新客户端」，历史全断。

改成**首次运行生成随机 uid**（`cli_<hex>`）并落盘：

```json
// state/client.json
{"uid": "cli_856358e3c709ab1ae4f5", "host": "DESKTOP-7EQOGAD", "created_at": "..."}
```

hostname 只作为**展示名**上报，不参与身份。这样改名不影响归属。

副作用（已写进使用说明的排查表）：**整份目录拷贝到另一台机器**，
`state/client.json` 会跟着过去 → 两台机器在后台显示成同一条。
解决办法是删掉副本里的 `state/client.json`，它会重新生成独立标识。

### 14.8 `account` 段为什么必须是「本机独占」

远端配置白名单（`server/app/managed.py` ↔ `stzb/remote_config.py`，两侧内容必须一致）
原本只排除了 `device` / `emulator` / `cloud` / `logging`。
这次把 **`account`（切换开关）** 也加进本机独占，理由值得单独记一笔：

- 服务端**能**指派「切到哪个账号」——那是**数据**（`clients.account_id`）；
- 服务端**不能**关掉「要不要切」——那是**控制权**。

如果服务端能关掉切换，那么一旦服务端配置被误改/被入侵，客户端就会
**停在别人的账号上跑任务**，而本机（人在外面，看不到）毫无察觉 ——
跑出来的都是别人账号的日常任务。这种「静默跑错账号」比直接报错危险得多。

所以：**凡是「关掉某项安全行为」的开关，都不给服务端。**
`tests/test_guardrails.py` 里有对应的回归测试，两侧白名单不一致也会被它抓到。

### 14.9 切换失败必须中止本轮，不能硬着头皮跑

`run_daily.py` 第 3.5 步（切换）放在 `ui.boot()` **之前** —— 因为「点击换区」
是登录页的入口，一旦进了主城就得先退出来才能切。

切换失败时直接 `_bail(5, ...)` 中止本轮，而不是继续：

- 账号不对 → 跑的是**别人的**日常任务，结果毫无意义还可能有副作用；
- 报告里会写清「切换结果」那行原因，后端也能看到（心跳状态里带 `switch: failed`）。

宁可不跑。一个「什么都没做」的报告，比一个「在别人账号上跑了一半」的报告好得多。

## 十五、冷启动真正的拦路虎：标题页与网易登录页（2026-09-19 新增）

第十二章讲了怎么把模拟器和游戏**拉起来**，但「拉起来」离「进了主城」还有三屏。
这一章记的是 2026-09-19 中午那次真机实测 —— 冷启动第一次被完整考验，暴露出两个
**之前一直没被发现**的 bug，因为它们只在「游戏完全没在跑」时才出现。

> 之前的几轮「实测通过」其实都站在 12:00 档/00:00 档的既有进度上：游戏本来就在主城，
> `boot()` 第一帧就 `is_home` 通过、直接 return，那两个界面**根本没走到**。
> 教训：**没从零冷启动跑过一轮，就不算验证过启动链路。**

### 15.1 症状：300 秒启动超时，日志全是「认不出的界面」

```
[12:56:32]     · 等了 8 轮仍认不出界面 → 强制清屏退回主城
[12:56:34]     · 认不出的界面 → 依次试右上角 ✕
...（每 5 秒盲点一次右上角，直到 300 秒超时）
[13:02:43] !! 启动超时
```

关键在于 `boot()` 每轮都会打印「识别到 N 行文字」，而那一屏是 **0 行 / 1 行**：

```
[12:55:44]     等待中…（识别到 1 行文字）
[12:56:02]     等待中…（识别到 0 行文字）
```

**OCR 读到 0 行，是判断「这是什么界面」的第一线索**，不该被当成「什么都不用做」。

### 15.2 第一屏：标题页「点击以开始游戏」——金底金字，全屏 OCR 读 0 行

冷启动时序：黑屏 → 网易游戏开屏（白底）→ **游戏标题页** → 网易统一登录页 → 主城。

标题页是一整张山水画，底部一行金字「点击以开始游戏」，**点屏幕任何地方都能过**。
但它是金底金字、底图又是同色系山水，对比度极低 —— 全屏 OCR 直接返回 0 行。

#### 为什么没用 OCR 兜底（试过，不行）

先试了「裁底部条带 + 放大 2.5 倍 + 增强对比」再 OCR。结果**极不稳定**：
同一批 17 帧里，逐字符覆盖率在 `0.00 ~ 1.00` 之间乱跳，只有 8 帧能读准。
艺术字 + 低对比度，OCR 天生不适合作这种判据。

#### 最终方案：模板匹配

同一批 17 帧用模板匹配打分，区分度**干净得不像话**：

| 帧类型 | 分数区间 |
|---|---|
| 标题页（12 帧） | **0.85 ~ 1.00** |
| 黑屏 / 网易开屏（5 帧） | 0.22 ~ 0.42 |

阈值取 **0.70**，两边各留一大截余量。

```python
# stzb/ui.py
TITLE_TAP = (960, 540)        # 标题页点哪都行，点中心最稳

def title_page_hit(self, path):
    img = read_png(path)
    hit = self.tpl.find(img, "title_page", roi=(0, 860, 1920, 200), threshold=0.70)
    return hit
```

模板文件 `templates/title_page.png`（115×660）是从真机截图里切出来的，
含金字标题 + 一点底图上下文，提高定位稳定性。

> **顺便给 `Templates.find` 加了 `threshold` 参数**：底图有噪声的模板
> （比如这行艺术字）用自己的实测阈值更稳，不必迁就全局默认的 0.82。
> 原来 0.82 对本例只剩 0.03 余量，太险。

### 15.3 第二屏：网易统一登录页 —— 「登录」二字被三个词污染

标题页过了之后，游戏进入**网易统一登录页**（有「常用」页签、脱敏账号
`159****4508`、「登录」按钮、「其他账号登录」）。

而 `boot()` 原来只认「开始游戏」四个字 —— 这是**手机版登录页**的按钮，
网易账号页上没有它，于是又卡住。

#### 为什么不能直接 `find_text(items, "登录")`

界面上含「登录」二字的东西有一堆：

- `自动登录`
- `上次登录刚刚`
- `其他账号登录` ← **点了会走去密码登录流程，脚本没有密码，必然卡死**

模糊匹配会挑错。所以判定必须**多信号投票**（判据与 `account.py` 一致）：

```python
def is_netease_login_page(self, items):
    texts_ = [norm(it.text) for it in items]
    if any("其他账号登录" in t or "其他帐号登录" in t for t in texts_):
        return True                       # 铁证
    if find_masked(items) is not None:    # 读到 159****4508
        return True                       # 铁证
    if any(t == "常用" for t in texts_) and any("网易" in t for t in texts_):
        return True
    return False
```

点「登录」也要精确 —— 复用 `core.find_login_button()`（见 15.5）。

> ⚠ 登录页上**永不发 Android BACK**：会弹「导致中途退出的原因是？」问卷，
> 里面就藏着「提交并退出」，点错等于自己把游戏退了、整轮任务全废。

### 15.4 第三屏之后才轮到「开始游戏」

完整的冷启动界面链（每一步都要能认出来，缺一步就卡到超时）：

```
标题页(模板匹配) → 网易登录页(多信号) → [手机版登录页: 开始游戏] → 资源下载/公告 → 主城
```

注意**顺序**：`boot()` 里「网易登录页」的判定必须放在「开始游戏」**之前**，
因为网易页上没有「开始游戏」，反之手机版登录页上也没有「其他账号登录」，
两者不会互相误判。

### 15.5 顺手做的重构：把共用判据提升到 core

「精确找登录按钮」和「抠脱敏账号」原来只写在 `account.py` 里，
现在 `ui.py` 的启动引导也要用同一套逻辑。为避免**两处判定漂移**
（这类漂移极难查），把它们提升到 `stzb/core.py`：

```python
core.find_login_button(items)   # 排除 自动登录/上次登录/其他账号登录
core.mask_of(text)              # 159****4508 / a***@qq.com
core.find_masked(items)
```

`account.py` 里保留同名薄封装（`_find_login_button` 等），行为完全一致。

### 15.6 第四个 bug：右下角「招募」偶发漏读 → 主城被误判

冷启动修好之后，12:00 档跑到市井时报「**打不开内政面板**」，
而**同一轮**的演武、特性都成功进去了 —— 概率性失败。

翻帧找到了根因：`is_home()` 要求必须读到右下角的「招募」按钮，
但那个按钮**会偶发漏读**（美术字 + 底图噪声）。漏读时：

```
is_home=False → open_neizheng() 以为人还在外面 → 反复退回主城重进 → 放弃
```

修法：加第二判据 —— 顶栏那个**短的**「势力值」标签（子面板顶栏没有它）。
关键是「**短的**」：活动面板说明长句里也有「势力值」三个字，
子串匹配会给它 0.909 分，不加长度闸门就会把活动面板误判成主城。

```python
def _short_has(self, items, kw, maxlen=10):
    """只在短标签里匹配。主城顶栏是「势力值21」这种短标签；
    活动面板那句「…提升势力值可获得势力积分…」必须被长度闸门拦掉。"""
```

改了之后用真机截图集回归验证：关键正样本 2/2 修好，
负样本误判**从 18 张降到 18 张（没有增加）**，而那 18 张实为
「主城 + 浮层」的过渡帧，判成主城反而是对的。

### 15.7 结果

同一个 12:00 档，冷启动全链路：

## 十六、控件树到底能不能用？一次把话说死的实测（2026-09-19 新增）

### 16.1 起因

有人问：除了 ADB + OCR + 图像识别，还有没有更好的识别技术？
按「信息源分层」的思路，往上还有**控件树（UIAutomator / 无障碍）**、
**通信协议（抓包）**、**内存（Frida）**。控件树是最划算的一档 ——
免费、快（0.1~0.3 秒）、稳定，工业界的第一层兜底就是它。

问题是：**这个游戏到底有没有控件树**？不能猜，得测。

### 16.2 实验设计

写了一个 `probe_full.py`，在**同一个进程**里（规避模拟器回收，见 `tools/README.md` 坑 1）：
`detach` 拉起 MuMu → `adb connect 16384` → 强杀游戏并重启 → 轮询 `mCurrentFocus`
等它进游戏 → 跑 `ui.boot()` + `open_neizheng` / `open_sub` / `open_recruit`，
同时 **monkey-patch `Ui.ocr`**，在每次 OCR 调用时同步采一次
`uiautomator dump` + `dumpsys window | grep mCurrentFocus`。

这样拿到的不是「某一屏的快照」，而是**整条每日任务链路上的逐帧采样**。

对照组：同样方法采 MuMu 自家启动器（原生 App）。

### 16.3 结果：控件树对这个游戏**完全无效**

| 采样对象 | 节点数 | 有文字 | 有 resource-id | 可点击 |
|---|---|---|---|---|
| 率土之滨（**50/50 帧**） | **5** | **0** | **0** | **0** |
| MuMu 启动器（原生 App，对照） | 76 | 19 | 54 | 25 |

50 帧覆盖了从「点击开始」到「主城 → 内政 → 税收 → 市井 → 演武 → 招募」
的完整流程，**每一帧都是 5 个节点、0 个文字**，且 50 帧的 dump **字节完全一致**。

原因很清楚：率土之滨是网易自研引擎游戏，**整个 UI 是引擎自己画到一个 SurfaceView 上的**，
Android 的控件树里只剩一个 `android.view.View` 容器，游戏内容对无障碍层完全不可见。

**`mCurrentFocus` 也一样**：游戏内 50/50 帧恒定是
`com.netease.stzb.netease/com.netease.stzb.Client`，
**不随游戏内界面切换而变**。

（顺带排除了一个误判：一度怀疑「50 帧一模一样」是游戏卡死了，
于是对比了 142 张截图的 md5 —— 画面确实在变。dump 一致是真实的，不是卡住。）

### 16.4 结论与取舍

- **控件树这条线，对游戏内容判死刑**：找按钮、判界面，只能用**画面层**
  （OCR / 模板 / 颜色 / 几何），这条路没得省。
- **但它能回答另一个问题**：`mCurrentFocus` 的**包名**能可靠回答
  「**游戏到底在不在前台**」—— 桌面 / 启动器 / 游戏三者区分得很干净。
- 于是「同时应用」在本项目里的正确形态是 **分工**：
  **画面层判界面**（主），**dumpsys 只当门卫**（判前台）。

「统一分层兜底识别接口」这个需求因此**收窄**：对游戏内容而言它只剩画面层一层，
没必要为控件树/协议层预留接口；真正值得留的就一个前台把关。

### 16.5 顺手补上的真 bug：游戏没起来时盲点空转

实测撞到：模拟器起着、**游戏没起来**时，OCR 读到的是 MuMu 桌面/启动器，
而 `boot()` 会一路走「认不出的界面」分支**盲点右上角 ✕**，
直到 300 秒超时 —— **空转 7 分 48 秒**，什么都没干成。

修复（三处）：

- `core.py` 加 `foreground_pkg()` / `foreground_activity()` / `game_foreground()`；
- `ui.py` 加 `Ui.game_foreground(ttl=3.0)`（TTL 缓存 + 异常放行）；
- `boot()` 循环开头加前台把关：不在前台就重新拉起，连续 3 轮不在前台则放弃。

**关键设计**：读不到前台信息时返回 `True`（**放行不误拦**）——
它的职责是防明显空转，不是安全阀（安全阀另有 `never_tap` 管）。
另外 `is_home` / `is_neizheng` **绝不能**依赖前台信息，它们判的是「界面」不是「进程」，
自检里专门加了断言钉住这条边界。

### 16.6 离线断言与验证

`tools/selftest.py` 新增 `test_foreground_guard()`（总数 343 → **359**，16 项断言），
输入用的是**真机抓下来的 dumpsys 原文**（游戏 / 启动器 / 桌面三份），
覆盖：包名与 Activity 解析、三态判定、边界（`is_home` 不得用前台）、
TTL 缓存、异常安全。

端到端验证：`run_daily.py --slot 12:00 --force --cold --keep-running`
单进程跑完 → **6/6 成功、355.8 秒、无回归**，前台把关未触发（游戏正常在前台）。

## 十七、磁盘治理：日志与截图的可配置保留（2026-09-19 新增）

### 17.1 问题：磁盘杀手是**截图**，而且它从来没人管

需求原话：「保存的日志和截图可以设置调整保存多少天，不能堆积的越来越多浪费空间。」

动手前先量了一下，结果很直接：

| 目录 | 会话开始时 | 说明 |
|---|---|---|
| `logs/shots/` | **2576 个 / 5.5 GB** | 单张 2~3.7 MB，**无任何清理逻辑** |
| `logs/reports/` | 21 个 / 22 MB | 只有一小段「删过期 `run_*`」 |
| `logs/diag/` | 16 个 / 24 MB | 人工侦察产物 |

跑了**两天**就堆到 5.5 GB。原因不是配置没写 —— `config.json` 里一直有
`logging.keep_days: 14`，但那段代码**只清理报告目录**，`shots/` 根本没接入。

顺带发现第二个问题：**`logging.save_screens` 是一段死配置** ——
从 `DEFAULTS` 定义到任何实现，**全项目没有一处读过它**。改了没有任何效果。
这属于「看起来有开关、实际是装饰」的典型，比没有更糟（让人以为关掉了其实还在存）。

### 17.2 设计：只删「自己认识的文件」

清理逻辑写错就是删用户数据，所以规则全部按**白名单**来（`stzb/cleanup.py`）：

| 目录 | 只清理什么 | 永不触碰 |
|---|---|---|
| `shots/` | 图片后缀（`.png/.jpg/.jpeg/.bmp/.webp`） | `_` 开头（侦察对比图） |
| `reports/` | `run_` 前缀 | `latest.html/.json/.md` |
| `logs/` | `run_*.log` | `console.log` |
| `diag/` | 图片后缀 | `.py`、子目录（人工证据） |

再加三条硬规则：
- **只删文件，不删目录** —— 任何 `isdir()` 一律跳过（不做递归删除）；
- **不跟随符号链接** —— `islink()` 直接跳过，防止顺着软链删到目录外；
- **只扫一级目录** —— 已知结构都是平铺的，递归只会增加危险。

### 17.3 体积上限：当天文件**永久豁免**

单纯按天数不够 —— 某天如果跑了十几次，光当天的量就能撑爆磁盘。
所以加了第二道阀 `shots_max_mb`（默认 3000 MB）：超了就从**最老**的开始删。

关键细节：**体积清理只从「非当天」的文件里挑**。
否则「今天跑超了 → 把今天的截图删了」会很荒谬 —— 你刚排完障想看截图，
发现被自己的清理逻辑删了。当天豁免让这条永远不会发生。

### 17.4 语义坑：`-1` 和 `0` 完全是两回事

配置项 `shots_keep_days` / `log_keep_days` 需要表达三种意图：
「跟主天数走」「独立设一个天数」「这条不清理」。JSON 里用 `null` 不直观，
用 `0` 又会和「不清理」撞车。最后的约定：

- `-1` = **跟随** `keep_days`
- `0` = **不按天清理**（这条不动）
- `> 0` = 独立天数

`cleanup.parse_cfg()` 专门做这个翻译，自检里有一条断言钉住
「`0` 不能被当成 `-1`」—— 这两种误读造成的后果差距极大（一个清空、一个保留）。

### 17.5 为什么允许后端下发（安全边界的一次调整）

`logging` 原来在「本机独占」名单里，理由是「本机磁盘策略」。
这次把它移进了可下发白名单，判断依据是**改错的后果等级**：

| 段 | 改错的后果 | 归属 |
|---|---|---|
| `device` / `emulator` | 直接连不上模拟器，人在外面无法自救 | 本机独占 |
| `cloud` | 服务端把自己的凭据下发给自己（荒谬） | 本机独占 |
| `account` | 停在别人账号上跑任务且毫无察觉 | 本机独占 |
| **`logging`** | **最多磁盘占用不合预期，脚本照跑** | **可下发** |

同理 `save_screens` 也放行 —— 关掉只影响「能不能倒查」，不影响任务能否跑成。
客户端对 `logging` 用的是**键级白名单**（不是整段放行），
段里混进来的其它键（比如有人塞个 `adb_path`）会被切掉。

### 17.6 ★★ 事故：一次测试把真实截图删了 471 张

这是本次最该记住的部分。

**现象**：自检跑完后，`logs/shots/` 从 2576 个掉到 2107 个，
2026-09-18 的 471 张（约 1.1 GB）消失，只剩两个 `_` 开头的（受保护）。

**根因链（三环扣死，少一环都不会出事）**：

1. 新加的「磁盘占用与清理」菜单用**模块级 `ROOT`** 拼路径
   —— 而 `ROOT` 永远指向真实项目根，**不随测试隔离变化**；
2. 自检的 `run_menu()` 只 patch 了 `tool.CONFIG_PATH`（指向临时目录），
   以为这样就隔离了 —— 但清理根本没读 `CONFIG_PATH`；
3. 测试喂的按键串 `"...13\n1\n..."` 里，`13` 恰好是**我当天新加**的
   「磁盘占用与清理」、`1` 是「立即清理」→ 一步点进真实清理。

至于**为什么只删了 09-18 的**：清理逻辑本身完全按设计工作 ——
`shots_max_mb=3000` 超限 → 从最老的非当天文件开始删到低于上限 →
09-18 的 471 张正好够，就停手了；当天（09-19）的 2107 张因「当天豁免」毫发无伤。

**所以这不是清理逻辑的 bug，是测试隔离漏洞。**

**修复（四层，缺一不可）**：

```python
# ① 路径来源必须可被测试替换 —— 这是核心
def project_root() -> str:
    """= config.json 所在目录。清理路径一律从它派生，绝不用模块级 ROOT。"""
    return os.path.dirname(os.path.abspath(CONFIG_PATH)) or ROOT

# ② 标记「当前是不是隔离环境」
def in_sandboxed_root() -> bool:
    return os.path.abspath(project_root()) != os.path.abspath(_REAL_ROOT)

# ③ 危险菜单不再直接开删：先 dry-run 摆出「删多少、影响哪个目录」，要 yes 才执行

# ④ 自检里加隔离铁律断言（谁改回 ROOT 立刻红）
check("project_root() 跟随 CONFIG_PATH，不是真实项目根", tool.project_root() == tmp2)
check("清理目标目录不在真实项目根下", ...)
```

**推广成一条项目铁律**（已写进 `MEMORY.md`）：

> 凡写删除/覆盖类逻辑，**路径来源必须可被测试替换**，
> 且自检里必须有一条「隔离」断言盯着。模块级常量 + 只 patch 其中一个入口
> = 隔离形同虚设。

### 17.7 验证

`tools/selftest.py` 新增 `test_cleanup()`（总数 359 → **394**），覆盖：

- 过期删 / 未过期留 / 当天留；
- `_` 前缀、`latest.*`、`console.log`、`.py`、子目录**全部保住**；
- 体积超限时**从最老开始删**且**当天豁免**；
- `keep_days=0` + 不限体积 → 再老也不删；
- **幂等**（连跑两次，第二次删 0 个）；
- 目录不存在不抛异常；
- `-1` / `0` / 缺项三种配置解析语义正确；
- **隔离铁律两条**。

实测记录：清理前后目录对比确认隔离生效（2107/16/21 三次自检后完全不变）；
沙盒演练中老文件删、保护文件全留；体积上限停在 2 MB 且当天保住；
后端配置页能渲染并保存 `logging` 段；客户端过滤把 `logging` 白名单键放行、
段内核外键切掉、`device/account/cloud` 全拦。

```bat

```

20px 上下，容易整条漏读」），但只用在了 `tasks.py` 找按钮的两处
（税收格、招募价格）。**面板判定这条路（`ocrmulti` / `_in_panel` / `wait_for_cond`）
一次都没用**，一直裸跑原图 OCR。

```

  → _in_panel("税收") 判 False（锚点一个都没出现）
  → open_sub 以为「不在内政界面」→ 退回主城重进
  → 3 轮循环耗尽 → 「× 进不去「税收」」
```

**注意这是个「假失败」**：面板每次都开成功了，脚本自己把它关掉。
这也解释了为什么这个 bug 会「时好时坏」——同一面板不同帧的 OCR 行数在 1~12 之间摆。

### 18.5 ★ 顺手揪出的第二处误判：「可强征0/3」

扫描 164 张历史帧时发现另一处**方向相反**的错：

```
sub_pre_税收_1_2_027.png
  texts: 云魇丨奈子 | #2357115 | [在野] | 势力21 | 望3077/20000 | 。领地12/30 |
         ... | 17：47：36 | 可强征0/3 | 市井
  in_panel(税收) = True      ← 内政面板被当成「已经在税收面板里了」
```

原因：`_in_panel("税收")` 的锚点里放了 `"强征"`（来自税收面板那个付费
「20/强征」按钮）。而**内政主界面上税收入口底下挂着的状态标签**
文案会变 —— 见过 `「立即征收N/3」`、`「可强征N/3」`、`「可领取N/3」` 三种，
其中 `可强征N/3` 含「强征」二字，一旦内政帧 OCR 只读到 1 个锚点
（`_is_neizheng_screen` 认不出），就会误判成「已在税收面板」。

这个方向比第一个更危险：它不会报错，会**静默地在内政界面上找征收按钮**，
操作全部错位（`ui.py` 里 16.5 节记过同类事故）。

**修法**：去掉 `"强征"` 锚点。代价是放弃「付费强征按钮」这个信号 —— 可接受，
因为税收面板**三个格子永远各有一个「征收」标题**（`已征收`/`征收中`/`等待中`
那几格也在），`_count("征收") >= 2` 在任何状态下都成立，比「强征」稳得多。

164 帧扫描结果：旧锚点 1 帧误判 → 新锚点 **0 帧误判**。

### 18.6 修复：三处判定加放大兜底 + 锚点纠偏

```
stzb/ui.py
  ① PANEL_MIN_ITEMS = 4  ← OCR 行数少于它就算「没读全」
  ② _ocr_scaled(path)    ← 把已截好的那帧放大再认（不重新截图，避免坐标错位）
  ③ ocr_multi(..., scaled_fallback=)  ← 并集仍太少就把最后一帧放大重认并合并
  ④ open_sub.snap / open_neizheng 进出判定   → scaled_fallback=True
  ⑤ wait_for_cond(fn=...)  → scaled_fallback=True
  ⑥ _in_panel("税收") 去掉 "强征" 锚点
```

第 ⑤ 条是**实机跑第二遍才发现的**：第一次修完，`open_sub` 的预检/复检已经能认出
面板（`✓ 已进入「税收」` 出现在 5 次点击全失败之后），但 `click()` 的
`verify_fn` 走 `wait_for_cond`，那里还是裸 OCR，于是**照样白点 5 次、白花 45 秒**。

这不只是慢，还有**误触风险**：多点的候选坐标里第 5 个 (1767,535) 就是图标位，
面板已经打开时这些点击会落到**面板内容上**，而税收格旁边就是付费的「20/征收」。

### 18.7 实测效果

修完前后各跑一次单任务（`--only shuishou --force`）：

| | 修复前 | 修复后 |
|---|---|---|
| 进入税收面板 | 点 5 次全判「未生效」，45 秒后靠复检兜回来 | **一次点中 (1770,600)**，10 秒 |
| 整体耗时 | 95.6s（截图 27 张） | **51.7s（截图 10 张）** |
| 结果 | 靠兜底勉强 OK | `shuishou OK` |

任务自己的安全规则也守住了（当时三格分别是「已征收 / 征收中 / 等待中」，
没有免费次数）：

```
[00:47:49]   · 本帧没读到可点的「征收」，放大 2 倍再识一次…
[00:47:50]     · 放大后读到了 11 行文字
[00:47:50]   · 只剩要花虎符的「强征」，跳过（绝不点）
[00:47:50]   ✓ 税收完成，本次征收 0 次
```

### 18.8 附带修好的：清理异常不再吃掉收尾

第一次实跑还有一个**隐性次生事故**：收尾阶段 `_do_cleanup` 抛异常后，
后面的收尾全被跳过 ——

```
[00:33:36] · 清理策略：报告/日志保留 14 天…
（异常）
（没有「清理后占用」）
（state/last_run.json 没更新，还停在 2026-09-19）
```

后果是**「今天已跑」没记上** → 下次调度会**重复跑一整轮、重复领奖**。

修法：把 `_do_cleanup` 用 `try/except Exception` 包住，失败只记一笔。
（用 `Exception` 而非 `BaseException`，Ctrl-C 要能正常中断。）
同时 `RunLock.release` 这个 atexit 收尾改成吞 `BaseException` ——
它绝不该在退出时抛栈、污染退出码；删不掉也无所谓，`acquire()` 认得出
「pid 已不在」的残留锁并自动接管（自检第 16 组已断言）。

### 18.9 离线断言（总数 394 → 405）

`tools/selftest.py` 新增 `test_panel_ocr_fallback()`：

- 内政界面（锚点不足）+「可强征0/3」→ **不算**已在税收面板（钉住锚点纠偏）；
- 真税收面板 → 仍判「已在里面」；
- **三格全付费「20/强征」** → 仍认得出（钉住「去掉强征也安全」）；
- 原图只读到 1 行 → **自动补了一轮放大 OCR**；
- 放大结果并入后能认出面板（漏读不再误判）；
- 原图读得够多 → **不浪费**放大 OCR；
- 默认不开启 → 其它调用点行为/耗时不变。

### 18.10 沉淀成通用教训

1. **「进不去某个界面」先别改坐标** —— 先把失败那一刻的截图捞出来看。
   本次真凶是「进去了、自己不认」，改坐标会越改越偏。
2. **OCR 行数本身就是信号**：整屏只读到 1~3 行 ≠ 这个界面没东西，
   而是**这一路 OCR 失效了**。判定路径必须对此有兜底，而不是把
   「读不到」直接当成「不在这个界面」。
3. **兜底要覆盖「预检 + 校验 + 重试」全链路**：只修预检，校验那层会继续
   白点、甚至误触（本次白花 45 秒 + 存在点到付费按钮的风险）。
4. **锚点要选「在任何状态下都成立」的东西**：入口的状态标签文案会变
   （`立即征收` → `可强征` → `可领取`），别拿它当锚点；面板内**结构性**
   存在的文字（三格标题「征收」）才可靠。
5. **收尾步骤要容错**：清理/上传这类「外部依赖型」步骤一旦抛异常，
   不能连累 `save_state` —— 否则是「任务跑完了但记录没写」，
   下次调度重复执行，比直接失败更麻烦。

## 十九、12:00 档实跑排障（2026-09-20 中午）：一个纯浪费、一个真花钱

12:00 档比 00:00 档多一个「特性」。实跑结果表面全绿（**6 成功 / 0 失败**，471 秒），
但翻日志发现两处问题：一处白耗时间，一处**会花掉真金白银**。

### 19.1 白耗 70 秒：「军情批阅」战报弹窗认不出

开机阶段日志：

```
[12:50:12]     · 登录页 → 点「开始游戏」
[12:50:30]     等待中…（识别到 20 行文字）
[12:50:36]     等待中…（识别到 20 行文字）
...
[12:51:08]     · 等了 8 轮仍认不出界面 → 强制清屏退回主城
```

**连续 8 轮、每轮都识别到 20 行文字**却"认不出界面"—— 这不是 OCR 漏读
（放大 2 倍还是 20~21 行），是**根本没有对应的处理分支**。

截图 `boot_02_002.png` 一看就明白：那是游戏的「**军情批阅**」战报弹窗
（"主公，在你离开的4小时49分钟里，势力中发生了如下事情，请批阅！"），
底部一个大按钮「批阅」，右下角一个「今日不再弹出」复选框。

**为什么每轮都会遇到**：它在你**离开一段时间再回来**时弹出 —— 而挂机过夜正好
就是这个场景，所以**每轮开机必然撞上**。它的麻烦在于：

- 没有「取消 / 跳过 / 关闭」→ 关弹窗那条通用分支找不到目标；
- 没有「确定 / 确认 / 知道了」→ `close_info_popup` 也接不住；
- 于是只能等 `rounds >= 8` 走「强制清屏」。

**修法**：接进 `guard()`（弹窗守卫，启动/点击/等待/回主城/任务里都会过它），
返回新信号 `"junqing"`，动作为点「批阅」—— 照玩家的做法把战报收掉。

两个刻意的设计取舍：

1. **绝不勾「今日不再弹出」**。那会改掉玩家自己的游戏设置（当天再也看不到战报），
   脚本无权替用户做这个决定 —— 宁可每轮多点一次。
2. **判据不能只用「批阅」二字**：正文里有一整句「如下事情，请批阅！」。
   所以用只属于本弹窗的标题词（`军情总览`/`军情批阅`/`军情比阅`）判定这是哪个弹窗，
   而按钮则要求 `norm()` 后**完全等于**「批阅」（正文那句归一化后是
   「如下事情请批阅」，不会误命中）。

**负向验证**（这类「会不会误点」的改动必须做）：扫 1171 张历史截图、实 OCR 1024 张，
`guard()` 报 `junqing` 的共 11 帧，**逐帧确认全部含军情特征词，假阳性 0 帧**。

> ⚠️ 踩坑记录：第一次做反例验证时我拿了 `home_00_009.png` 当"主城帧"，
> 结果它也触发了、差点当成假阳性去改代码。真相是**那个文件本身就是战报弹窗**——
> 截图文件名只是调用处的 tag（当时是 `to_home` 采的），**不代表画面内容**。
> 判断一帧是什么，永远要看图，不能看文件名。

### 19.2 ★ 会花真钱：绿标签把付费按钮认成了「免费」，三个安全阀全被跳过

招募任务的日志先报"按免费处理"，紧接着就要虎符：

```
[12:57:00]     · OCR 没读到「免费」二字，但按钮左边有绿色「免费」标签 → 按免费处理
[12:57:00]     · 还有免费次数，本次按免费处理
[12:57:00]     → 点「@1佣/招募1次」@(731, 912)（免费）
[12:57:05]     · 虎符不足 → 按配置兑换 100 虎符
```

**「免费」却需要虎符，这本身就是矛盾**，于是去查那一帧。

`rc_half_panel_137.png` 显示：按钮是「**100 / 招募1次**」，左边一个**绿色圆形货币图标**，
下方贴着红色「**打折**」标签 —— 这是一次**付费半价**抽取。

而「免费」二字的 OCR 死活读不出来（白字压饱和绿底、字号又小），
所以代码只能靠**颜色+形状**认那枚绿标签（`_has_free_badge`）。
实测两个样张一比，判据根本分不开：

| | 面积 | 宽×高 |
|---|---|---|
| 真免费标签 | 639 | 40×32 |
| 付费货币图标 | 658 | **34×40** |

判据区间是「面积 ≥250、宽 22~80、高 18~55」—— **两者完全落在里面**。

**后果为什么严重**：`is_free=True` 会让代码直接走 `if is_free` 分支，
于是半价轮的**三个安全阀被整段跳过**：

```
if is_free:
    log("还有免费次数，本次按免费处理")     # ← 从这里出去，下面全不执行
else:
    if discount is None and not ribbon and not offer_txt: → 不抽
    price = _read_recruit_price(...)                        → 读不出就不抽
    if price > cap:                                         → 超上限就不抽
```

也就是说脚本会**盲点一个付费按钮**。实测当场撞上「虎符不足」并兑了 100 虎符，
换来的是一次**未经价格校验**的抽取。更坏的情形（没细看那一次的确切价格）是：
若按钮是原价 200，脚本会先兑 100 虎符、再发现仍不足而放弃 ——
**白花 1 玉符 / 100 虎符，什么都没抽到**。

**修法**：加一层交叉验证 —— 绿标签说"免费"时，再看按钮**紧邻处**有没有「打折」。
有就改判为付费（`_free_claim_is_trustworthy`）。

半径刻意取 `dx=240 / dy=150`，**比半价安全阀的 460 小得多**：
太大就会把旁边卡包卡片上的「打折」也吃进来，反过来把真免费的那一轮误杀
（那是白丢一次免费抽）。实测半价帧：按钮 (731,912)、「打折」(556,856) → dx=−175, dy=−56。

验证（同一帧、修复前后）：

| 帧 | `is_free` | 价格 | 结论 |
|---|---|---|---|
| 真免费 | True | — | 抽（免费） |
| 半价 | **False**（交叉验证改判） | **100** | **抽（半价，100 ≤ 上限 100）** |

### 19.3 顺带修好的第二个：这一屏的**价格根本读不出来**

修完 19.2 会发现另一个问题：安全阀跑了，但 `_read_recruit_price` 返回 `None`，
于是"读不出价格 → 不抽"（安全，但配置里开着的半价抽卡就永远抽不了）。

原因是**游戏有两套招募 UI，价格排布不同**：

- 招募列表页：价格在按钮**下方**（`_price_under_btn`）—— 现有代码只认这种；
- 卡包详情页：价格在按钮**同一横行、文字左侧**（「100 / 招募1次」）。

而这一屏 OCR 在 1x 下把整条读成 `@1佣/招募1次`（`100` 糊成 `@1佣`），
放大 2 倍才读成 `》@100/招募1次`。

**修法**：新增 `_price_in_btn_row()`，用**结构正则**抠价格：

```python
RC_PRICE_ROW_RE = re.compile(r"(\d{2,4})\s*[-~〜]?\s*/\s*招募\s*[1-5]\s*次")
```

⚠️ **关键点：不能只扫这一行里的数字**。OCR 会把价格和按钮文字并成一条
`》@100/招募1次`，里面的「1次」也带数字 —— 直接取 `min()` 会读成 **1**。
读成 1 比读不出来**更危险**：安全阀「价格 ≤ 上限」会永远通过。
所以必须用「数字 + `/` + 招募N次」这个结构去锚定。

验证：`》@100/招募1次 → 100`、`《@950/招募5次 → 950`、
而 1x 的 `@1佣/招募1次 → None`（**绝不能是 1**，这条有断言钉着）。

### 19.4 沉淀

1. **「免费」判定不能只靠颜色**：颜色分不开的东西，要找一个**同屏的语义信号**
   做交叉验证（这里就是 OCR 能读到的「打折」二字）。
   颜色只是线索，不能当结论。
2. **判据区间被"另一个东西"落进来，就是设计缺陷**。免费标签与货币图标的
   面积/宽高完全重叠 —— 这种判据即使当下能跑，也迟早翻车。
3. **安全阀的 bypass 路径要单独审**：`if is_free:` 这种"早退"分支会让后面
   一整串校验形同虚设。凡是「跳过多重安全检查」的分支，都要问一句
   「这个条件会不会被误判？」。
4. **OCR 里取数字必须带结构锚点**。裸扫数字取 min/max 都可能读出量级错误的
   数值，而"看起来合理的错值"比读不出来危险得多。
5. **别拿截图文件名当画面内容**（19.1 的踩坑）。文件名是调用处的 tag。
6. **每轮都会遇到的东西，值得单独写一个分支**。「军情批阅」命中率 100%
   （挂机过夜必弹），却要白等 70 秒 —— 这种"每轮都亏"的账，越早算越省。

## 二十、账号 / 角色切换的真实机制（2026-09-20 实机勘查）

这一章是**推翻旧假设**的一章。起因是「后端添加新账号 → 识别新角色 → 下发任务」
这条路从来没在真机上跑通过（后端数据库一直是空的），于是从头把游戏的登录链路摸了一遍。

### 20.1 登录链路是**三屏**，而且主城是「回不去」的那一屏

```
主城  ──（没有任何回登录页的入口！）──►  ❌ 走不通
主城  ──重启游戏进程──►  标题页  ──点中央──►  游戏登录页
```

两屏都长得像「登录页」，之前一直混着：

| | 网易统一登录页 | **游戏自己的登录页** |
|---|---|---|
| 特征文字 | 「网易游戏」logo、脱敏账号 `159****4508`、「常用」页签、「登录」、「其他账号登录」 | 底部「[经典服] X6014 龙兴之地 征服 \| **点击换区**」、「开始游戏」 |
| 有「点击换区」吗 | **没有** | **有（只在这一屏）** |

**所以：任何「切区服 / 列角色 / 切角色」的动作，都必须先站到「游戏自己的登录页」。**

### 20.2 ★ 根因：主城上 (60,62) 是「任务」按钮，不是用户中心

`account.LOGIN_ACCOUNT_ICON = (60, 62)` 是**登录页左上角的账号图标** ——
但**主城**左上角同一位置是「**任务**」按钮（实测两者的可点区域只差 ~40px）。
所以从主城调 `_open_user_center()` 必然点开「任务」面板，然后报
「当前不在登录页，也打不开用户中心入口」。

**而主城上根本没有回登录页的入口**（用户中心只存在于标题页/登录页）。
这就是「切不了账号/角色」的真正原因。

**修法**：`restart_game_to_login()` —— 重启**游戏进程**（十几秒；不必重启模拟器，
那是 1~2 分钟）：`force-stop` → `launch` → 标题页（模板匹配）点中央 → 必要时点
「登录」→ 登录页。`ensure_game_login_page()` 先试用户中心，失败就自动退回这条路。

> 沉淀成规则：**换账号/换角色，一律从「重启游戏到登录页」开始**，
> 不要再指望从主城一路点回去。

## 二十一、从「心跳轮询」改成「实时长连接」（2026-09-20 晚）

这一章记一次**架构改动**：把客户端与后端之间「每 30 秒问一次」的心跳，
换成了以 WebSocket 长连接为主的实时通道。

### 21.1 原来的问题：后端完全被动

原设计里后端不能主动连客户端（NAT / 防火墙），所以所有交互都是
「客户端定时来问」：

```
客户端 ──每 30 秒 POST /api/agent/ping──► 后端
         ◄── 顺带捎回：指派 / 是否要切换 / 一次性指令 ──
```

于是管理员在控制台点了「立刻跑一轮」，**最坏要等 30 秒**客户端才来问；
点「探测界面」同理。而且 `run_daily.py` 跑完就退出，剩下 20 多个小时里
后台既看不到它、也推不动它 —— 想让某台机器现在就跑，只能干等下一档。

### 21.2 改法：长连接为主，心跳兜底

```
                 ┌── WebSocket /api/agent/ws（主）──►  后端**主动推**
客户端（常驻代理）│                                       派任务 / 下指令 / 改指派 / 改配置
                 └── HTTP 心跳 /api/agent/ping（兜底）──►  只在长连接断了时启用
```

**心跳绝对不能删** —— 这跟「懒」无关，是环境决定的。WS 会被一堆东西挡掉，
而且都不是「配置错了」，是环境本来就这样：

- 企业防火墙 / 出口设备掐掉非 HTTP 的 `Upgrade`；
- **反向代理没配 `Upgrade` / `Connection` 透传**（最常见的翻车点）；
- 杀软 / 上网行为管理拦长连接；
- NAT 网关掐空闲连接；换 WiFi / VPN 重连时连接直接断。

所以最终形态是「WS 优先 + 心跳兜底 + 退避重连」：
WS 连着走 WS；WS 一断**立刻**退回原来的 HTTP 心跳（在线状态不断档），
同时按 1/2/4/8/15/30 秒退避重试长连接。两种模式下客户端能力完全一样，
只是快慢不同。

### 21.3 ★ 两条硬规矩

**规矩一：数据库始终是唯一事实来源。**

实时通道只负责「通知」，绝不负责「存东西」。待领任务仍在 `run_requests` 表，
一次性指令仍在 `clients.probe_json`，配置仍在 `configs` 表。
推送的消息只带一句「有新东西了，你来看看」，客户端收到后照常走原来的
HTTP 接口拉。

换来两个好处：**连接断了不会丢任务**（只会慢一点），以及以后想换传输层
（长轮询、gRPC、消息队列）一行业务代码都不用动。

**规矩二：状态计算只能有一份。**

「这台客户端现在该收到什么」（指派 / 是否要切换 / 有没有指令）这段逻辑，
HTTP 心跳和 WebSocket **共用同一个 `build_client_state()`**
（`server/app/routes_agent.py`）。

这不是为了少写几行 —— 是因为两处各写一遍迟早会分叉，而分叉的后果是
**同一台客户端走长连接和走心跳拿到不一样的指派**，只在某一条通道上复现，
极难排查。护栏测试 `test_realtime_contract` 里有一条断言专门盯着它
（检查 `_heartbeat` 的源码里确实调用了 `build_client_state`）。

客户端侧同理：`Realtime._apply()` 处理服务端给的那一坨，
**不允许出现「如果是 WS 就……否则……」这种分支** —— 两条通道收到的
本来就是同一个函数算出来的东西。

### 21.4 服务端：从同步路由跨线程推到协程里

管理端的路由是**同步函数**（FastAPI 丢在线程池里跑），而 WebSocket 是**协程**。
所以推送不能直接 `await`，也不能直接往 `asyncio.Queue` 里 `put`
（`asyncio.Queue` 不是线程安全的）。

做法是在 lifespan 里记住事件循环对象，推送时用
`loop.call_soon_threadsafe(queue.put_nowait, msg)` —— 这是官方指定的
「从别的线程往事件循环里塞回调」的姿势。每条连接自带一个队列，
由它自己的写协程消费。

踩到的第一个坑就在这：`notify_all()` 一开始写成
`sum(_deliver(u, what, **extra) for u in uids)`，而 `_deliver` 的签名是
`(uid, msg)` —— `**extra` 全被当成了关键字参数，直接
`TypeError: got an unexpected keyword argument 'job'`，
**管理端派任务返回 500，客户端一条通知都收不到**。
而且 uvicorn 的访问日志里只有一行 `500 Internal Server Error`，
堆栈被输出缓冲吞了，最后是在进程内用 `TestClient` 复现才看到。
教训：**跨线程推送的接口要定死，别用 `**kwargs` 一路透传。**

### 21.5 客户端：纯标准库的 WebSocket

客户端脚本的原则是「拷到任何一台 Windows 机器、不装任何额外依赖就能跑」，
所以 `stzb/ws.py` 全部依赖是
`socket / ssl / struct / hashlib / base64 / secrets / threading` —— 标准库。
不引入 `websocket-client` 之类，就是为了不破坏这条原则。

实现范围：握手（`Sec-WebSocket-Accept` **逐字节核对**）、五种操作码、
长度三档、分片、控制帧插队、8MB 单帧上限、握手后残留字节缓冲；
不做扩展协商、子协议、代理隧道（都没用到）。

#### ★ 这里有一条最容易被「优化掉」的规矩

长连接上要一边收消息一边做别的事（发保活、推状态），所以 `recv()` 必须能
「等一小会儿没消息就先返回」。于是就有了这个陷阱：

```
假设一帧这样到达 —— 第一次 recv 只拿到前 3 个字节（帧头都没读完）。
如果这时把已读的字节从缓冲区拿走，下次就会**从帧的中间**开始解析：
负载被当帧头、长度字段被当操作码 —— 一串莫名其妙的错误，
而且**偶发**：取决于操作系统这次把多少字节塞进同一个 TCP 段。
```

所以 `_try_parse()` 的规矩是：**帧不完整就返回 None，且一个字节都不动**。
超时/中断后下次重新从头解析 —— 天然幂等，不存在错位。
代价只是把已有的几百字节重解析一遍，完全不值得为这点开销冒上面的风险。

自检里有一条断言专门钉死它：喂半个帧 → 超时 → 断言 `_buf` **原封不动**
→ 补上另一半 → 能完整解出来。
（`tests/test_realtime.py` A 段，用 `socket.socketpair()` 造真 socket 测，
不需要起服务。）

### 21.6 顺手修掉的两个真 bug

**（1）控制台 CSP 让全部交互静默失效。**

全局 CSP 原来是 `script-src 'none'`，而控制台页面里的交互全是**内联脚本**
和**内联 `onsubmit=` 确认框** —— 浏览器一律不执行，而且**页面上不报任何错**
（只有开发者控制台里才有）。后果里最严重的是：
「删除客户端 / 删除运行记录 / **轮换采集端令牌**」这些不可逆操作
**没有二次确认框**；角色下拉联动、在线状态自动刷新也全都没生效。

修法不是放宽到 `unsafe-inline`，而是：脚本一律搬到 `/static/console.js`
（外部同源文件），内联事件处理器改成 `data-confirm` / `data-*` 属性，
CSP 收紧成 `script-src 'self'` + `connect-src 'self'`。
**XSS 防护强度不变，功能真的能跑**。护栏测试里两条都钉住了：
CSP 方向（不许出现 `'none'` 或 `'unsafe-inline'`）+ 模板方向（零内联）。

**（2）客户端正忙时收到指令会「两边抢游戏界面」。**

常驻代理和 run_daily 都可能收到「探测 / 强制切换」。如果代理正在跑一轮任务
（或反过来），一边在点界面一边又被切角色 → 任务那边以为还在主城，
后面所有点击全部错位。

改法是引入一个 `BUSY:` 前缀：客户端判断自己正忙就回报
`BUSY: 本机正在跑任务…`，服务端收到后把指令**放回队列**（状态改回 pending），
等它闲下来自然会再取走执行。**管理端那一次点击不会白点**。
自检里有断言钉住两侧前缀一致（客户端 `stzb/realtime.py` 与服务端
`routes_agent.py`）—— 不一致的话，服务端会把「正忙」当成普通失败消费掉，
指令就永远不执行了。

### 21.7 「随时派任务」是怎么真正落地的

长连接本身只是让「收到」变快了，但要「派下来就能跑」，还需要有人**接着干活**。
这个角色是常驻代理 `agent.py`：

```
管理端派任务 → 后端推 notify("jobs") → 常驻代理收到
   → 检查本机有没有一轮在跑（共用 stzb.identity.run_in_progress）
   → 没有就起一个 run_daily 子进程（--job-only）
   → 那一轮跑完，代理再看一眼队列，还有就接着起（把积压排空）
```

三个刻意的设计取舍：

- **代理自己绝不碰游戏界面**（探测除外，那只是截屏 + OCR）。真正的点击全部
  交给 run_daily 子进程 —— 因为那里有单实例锁和完整的报告/上传逻辑，
  代理不必也不该重复实现一遍。
- **用 `--job-only` 起**，是为了防退化成常规运行：万一那条任务在这一瞬间
  被别人抢走或被取消，run_daily 必须**直接退出**，而不是顺势把「当前档位的
  常规任务」跑一遍 —— 那等于凭空多跑一轮，还会重复领奖。
- **「本机是否在跑」只有一处实现**（`stzb/identity.run_in_progress`），
  代理和 run_daily 共用。判据是「锁文件里的 pid 还活着 **且** 锁没超龄」，
  不是「锁文件在不在」—— 被强杀的进程会留下残留锁，拿「文件存在」当判据
  会把空闲机器判成忙，后台派的活就永远接不了。自检里这一组有 12 条断言，
  专门覆盖残留锁、坏锁文件、自己 pid 等情况。

> Windows 上探活**不能**用 `os.kill(pid, 0)`：Windows 的 `os.kill` 会把
> 非 `CTRL_*` 的信号实现成 `TerminateProcess` —— 探活探成杀人。
> 所以走 Win32 `OpenProcess` + `GetExitCodeProcess` 查是否 `STILL_ACTIVE`。

### 21.9 沉淀

1. **「推送」不能取代「状态同步」**。推送是尽力而为的（消息会丢、连接会断），
   所以真正的状态必须落在数据库里，推送只负责让「发现」变快。
   本项目里 `pending_jobs > 0` 也算一次「有新任务」通知 —— 只要有一次状态
   同步成功，队列里的活就不会被一直晾着。这就是
   **「拿不到 notify 也能跑」**该有的样子。
2. **兜底路径要和主路径共用同一份逻辑**。走 WS 和走 HTTP 拿到的必须是
   同一个函数算出来的东西，客户端也必须用同一段代码处理 —— 否则
   「只在某条通道上复现」的 bug 会一直躲着。
3. **涉及「从别的线程推进协程」时，接口要定死**（`(uid, msg)` 这种），
   别用 `**kwargs` 一路透传：一个参数名不匹配就是 500，而且堆栈可能
   被日志缓冲吞掉，排查成本远高于省下的那几行。
4. **CSP 这类「安全配置」最容易造成静默失效**：不报错、页面上看不出，
   只有开发者控制台里才有。凡是「写了但看起来没生效」的前端行为，
   先看 CSP/控制台，别急着改 JS。
5. **「忙」这个状态要有明确的传播方式**。让客户端回报 `BUSY:` 并把指令
   放回队列，比「硬执行导致两边抢界面」和「直接失败丢掉指令」都好。

## 二十二、角色名里的「丨」：一个必然踩中的坑（2026-09-20 实机发现）

### 22.1 现象

游戏角色名大量用**中文竖线「丨」**(U+4E28) 当中缀 ——
`执剑丨青山`、`云魇丨奈子`、`鸡波长` 这类昵称在率土里非常常见。

实机验证时（连续三次 OCR）：

```
第1次: '执剑丨青山'  码点: U+6267 U+5251 U+4E28 U+9752 U+5C71
第2次: '执剑丨青山'  码点: U+6267 U+5251 U+4E28 U+9752 U+5C71
第3次: '执剑丨青山'  码点: U+6267 U+5251 U+4E28 U+9752 U+5C71
```

读出的是 **U+4E28**，不是渲染问题，是真的汉字。
（所以不能靠「换个字体」解决，也别怀疑 OCR 不稳 —— 它读对了。）

### 22.2 为什么这是个必踩的坑

**人在后台手打角色名时，几乎必然打成 ASCII 竖线 `|`** ——
两个码点长得几乎一模一样，屏幕上根本分不出来：

| | 码点 | Unicode 类别 | 眼睛看 |
|---|---|---|---|
| `丨` | U+4E28 | Lo（CJK 汉字） | 一条竖线 |
| `\|` | U+007C | Sm（数学符号） | 一条竖线 |
| `｜` | U+FF5C | Sm（全角） | 一条竖线 |

而 `core.norm()` 是把「OCR 常见标点噪声」丢掉用的，`|` **在丢弃表里**、
`丨` **不在**。于是：

```
norm("执剑|青山")  →  "执剑青山"     ← ASCII 竖线被当噪声丢了
norm("执剑丨青山") →  "执剑丨青山"    ← 中文竖线留着
```

两边永远不相等。实测匹配分 **0.809**（完全一致才是 1.0）。
后果分两层，都很难查：

1. **后端会把同一个角色当成两个人**：登记「执剑|青山」、OCR 报「执剑丨青山」，
   `role_key()` 算出来不同 → **自动发现会重复建角色**；
2. **指派比对永远不等** → `switch_needed` 一直是 true → **天天白切一遍**。
   这正是「角色名=身份、区服=到达手段」这套设计最想避免的事
   —— 本来是为了「合服不改名」才只认名字，结果被一个竖线破了功。

### 22.3 修法

在**两侧**各加一个「竖线归一化」，并且**比较之前先统一**：

```python
# 只归一只确定是竖线形状的字符
_VERT_CHARS = "|丨｜│┃∣❘ㅣǀ"
_VERT_RE = re.compile("[%s]" % re.escape(_VERT_CHARS))
```

| 位置 | 改了什么 |
|---|---|
| `stzb/account.py` | 新增 `_norm_vert()`；`_one_score()` **先统一再 norm**（顺序不能反）；`_clean_role_name()` 顺手统一，让上报的名字形状一致 |
| `server/app/db.py` | 新增 `normalize_vert()`；`role_key()` 里「去空白 → **统一竖线** → 转小写 → 剥区服前缀」 |

**顺序为什么不能反**：`norm()` 会丢掉 ASCII `|`。
若先 `norm` 再统一，`|` 早就没了，统一也救不回来。所以必须
`norm(_norm_vert(text))` 这个嵌套顺序。

### 22.4 ★ 反向护栏：绝不能顺手把字母也「归一化」

`I`（大写 i）、`l`（小写 L）、`1` 在某些字体下也像竖线 ——
但它们是**角色名里可能真正出现的字母**（`Iron`、`lulu`）。
把它们并进来，等于把「两个不同角色」判成同一个，**比原来的 bug 更严重**
（会切错号 = 在别人的号上跑任务）。

所以字符表里**只放确定是竖线形状的**，并写了断言防回归：

```python
for bad in "Il1":
    check("竖线字符表里不含字母/数字 %r" % bad, bad not in _A._VERT_CHARS)
check("「Iron」与「lron」仍是两个不同名字", _A._one_score("Iron", "lron") < 0.99)
```

护栏测试 `test_role_name_vertical_normalized` 还额外钉了两件事：
**两侧字符表必须一字不差**、**两侧归一化结果必须相同** ——
否则会出现「后端认为一致、客户端认为不一致」这种只在一边复现的分叉。

### 22.5 沉淀

1. **「看起来一样」和「码点一样」是两回事**。凡是让用户手输、又拿去和
   OCR 结果比对的字段，都要问一句：**用户会怎么打？机器会怎么读？**
   同形异码（Homoglyph）是这类系统的通病，竖线只是其中一种。
2. **归一化的顺序本身是逻辑的一部分**。`norm` 会丢字符，
   所以「先统一还是先丢噪声」不能凭感觉调 —— 错了就是静默不匹配。
3. **放宽匹配之前先想「最坏会怎样」**。把 `I`/`l` 并进来能让匹配更宽松，
   但最坏结果是**在别人的账号上跑任务**。所以宁可窄，不可错。
   这条和「同名歧义就拒绝猜测」是同一个价值观。
